## 1. 系统概述

### 1.1 定位

面向新能源汽车维修场景的多角色智能诊断平台。同一套服务端 Agentic RAG 诊断引擎，按角色呈现四种界面：

| 角色 | 使用者 | 看到什么 |
|---|---|---|
| 车主（owner） | 车主 | 对话式 AI 助手：描述故障 → 通俗三段式诊断卡（🟢🟡🔴 严重度 + 可能原因 + 检修步骤 + 待确认项）→ 需要检修时一键预约 |
| 店员（staff） | 维修技师 / 服务顾问 | 预约工单队列、车辆档案、AI 诊断摘要、证据链对话界面、案例沉淀、打印报告 |
| 管理员（admin） | 门店管理者 | 成员与角色管理、知识库管理（含检索测试台）、统计看板、审计日志 |
| 超级管理员（superadmin） | 仅部署者 | `/superadmin` 调试后台：模型供应商槽位与 Agent 运行参数在线配置、保存即热生效 |

### 1.2 商业闭环

一键预约是车主端与店员端的衔接点——它把"预约检修引导"升级为**携带诊断上下文的工单流转**：

```
车主端 AI 诊断 → 判断需检修 → 【一键预约】生成预约单（自动携带车辆档案 + AI 诊断摘要卡）
    → 店员端实时收到新单（30s 轮询提醒）→ 接单 / 改约 → 提前备件、到店直接对接
    → 回填维修结果 → 确认沉淀为门店案例 → 回流知识库检索范围（数据飞轮闭合）
```

### 1.3 设计原则

1. **单体应用**：一个 Python 进程同时提供 API 与前端静态托管，无 Docker、无外部中间件依赖（数据库 / 向量库 / 全文索引全在 SQLite 系内），换机器 = 拷目录。
2. **降级不中断**：任一外部依赖（压缩 / 嵌入 / 重排 / 小模型 / 联网检索）不可用只降级对应能力，主流程不停。
3. **密钥单一宿主**：全部密钥只存服务端 `data/config.json`，不进仓库、不下发前端、不写日志；前端构建产物零密钥。
4. **证据先行**：系统提示词强约束"无证据不下结论"——查资料、查码表、问当事人，唯独不凭训练记忆编造故障结论。
5. **可评测优先**：检索质量由红绿闸门守护（先于功能、可复现），"改坏检索而测试仍绿"被结构性排除。

## 2. 总体架构

### 2.1 进程模型

```
浏览器（PWA · 手机/桌面自适应）
   │  HTTPS（Cloudflare 边缘 TLS）
   ▼
FastAPI 单进程（python main.py，默认 :8600）
   ├── /api/*          REST + SSE 流式（JWT 四角色鉴权）
   ├── /superadmin     调试后台（同一前端工程的路由分区）
   └── /*              前端构建产物静态托管 + SPA fallback（同源直达）
   │
   ├── core/agent      Agentic 循环（工具调用 ≤6 轮 / 追问 ≤3 次）
   ├── core/tools      工具注册表（6 个工具）
   ├── core/providers  模型供应商（主对话 / 后台压缩 / 嵌入 / 重排 / 小模型 / Tavily）
   ├── rag             检索引擎（向量主路 + 云端重排 + BM25 降级保底 + 红绿闸门）
   ├── db              SQLAlchemy ORM（SQLite 单文件 + 轻量迁移）
   └── seed            演示账号 / 演示车辆 / 内置知识库语料

外部依赖（五模型槽位 + 联网检索，全部可在 superadmin 后台热切换）：
   主聊天模型（诊断推理 + function calling）
   后台压缩模型（长对话摘要；缺省跟随主对话配置，主模型可兼任）
   向量化模型（bge-m3，云端 API 或本地 llama-server）
   重排模型（bge-reranker-v2-m3，对 top_k 召回结果精排；不可用保持原序）
   小模型（状态卡抽取 + 会话标题，异步；缺省回退后台主对话模型，云部署免本地依赖）
   Tavily（联网核实，可选）
```

### 2.2 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | Python 3.12 + FastAPI（异步） | 单进程，SSE 流式输出 |
| 数据库 | SQLite + SQLAlchemy ORM | 单文件 `data/data.db`，启动时轻量迁移（检查并补列，非 alembic） |
| 向量主路 | sqlite-vec（vec0 虚表）+ 云端 bge-m3 嵌入 | 与业务库同文件零部署，语义检索主路（§5.2） |
| 重排 | 云端 bge-reranker-v2-m3 | 对向量召回 top_k 精排，不可用保持原序 |
| 关键词路（降级） | jieba 中文分词 + rank-bm25 | 内存索引，仅作嵌入不可用/零召回时的兜底 |
| 前端 | Vue 3 + TypeScript + Vite + Element Plus | PWA、手机/桌面自适应、vue-tsc 严格类型检查 |
| 认证 | PBKDF2-SHA256 + JWT | 详见 §9 |

## 3. 模型供应商体系

### 3.1 槽位划分

| 槽位 | 职责 | 同步/异步 | 缺省行为 |
|---|---|---|---|
| 主对话 | 诊断推理 + 工具调用 + 通俗摘要 | 同步（主链路） | 无降级——主模型不可用则本轮对话报错 |
| 后台压缩 | 长对话前情摘要 | 同步（触发时） | 地址/Key 缺省跟随主对话；失败降级纯轮数截断 |
| 嵌入 | 知识块与查询向量化 | 同步（检索时） | 不可用降级纯关键词检索 |
| 本地小模型 | 状态卡抽取初稿 + 会话标题 | **异步**（不阻塞主回答） | 缺省回退后台主对话模型（携带 thinking disabled）；回退也失败则自动跳过（标题用默认名、状态卡留空） |
| 联网检索 | Tavily web_search 工具 | 同步（工具调用时） | Key 缺失/失效自动禁用该工具 |
| 重排 | 对 top_k 向量召回结果精排 | 同步（检索时） | **已启用**（bge-reranker-v2-m3，实测 top1 82%→86%）；服务不可达/异常静默保持原序，检索不中断（§12-D4 演进） |

### 3.2 配置与热生效

- `data/config.json` 是唯一配置源（含密钥），启动加载一次、进程内共享同一 dict。
- superadmin 后台的修改直接写该 dict 并持久化；Agent 参数经 `agent_param()` **每次调用实时读取**——除 `server`/`security` 节外全部热生效，无需重启。
- 数字参数带**合法区间校验**，越界拒绝而非静默钳制（避免"以为改成了 3 实际被钳成 6"）。
- 每个供应商槽位带「测试连接」实测；Key 单向掩码展示，留空即不修改。

### 3.3 参数缺省值（superadmin 可调）

| 参数 | 缺省 | 含义 |
|---|---|---|
| max_tool_rounds | 6 | 单轮用户消息允许的工具调用循环上限 |
| max_ask_user | 3 | 单轮 ask_user 提问上限 |
| max_tokens / temperature | 2000 / 0.6 | 主模型单次回复上限 / 采样温度 |
| tool_result_max_chars | 4000 | 单条工具结果截断 |
| compress_max_rounds | 20 | 压缩阀门 1：保留最近轮数 |
| compress_token_budget | 24000 | 压缩阀门 2：进上下文的估算 token 上限 |
| compress_min_keep_rounds | 4 | 阀门 2 触发时最少保留轮数 |
| summary_max_chars | 800 | 前情摘要长度约束 |
| force_first_round_search | false | 首轮经 API 层 `tool_choice` 硬强制 kb_search |

## 4. Agentic 诊断引擎

### 4.1 Agent 循环

```
用户消息 ──► [首轮可选：tool_choice 硬强制 kb_search（兜底预检索）]
   │
   ▼
主模型（系统提示词 + 工具清单 + 上下文）
   │  自主决定：调工具 / 追问 / 出结论
   ▼
tool_calls 执行回填 ──► 证据不足则改写查询再查（多跳：码表 → 知识库 → 联网）
   │                    （安全阀：≤6 轮工具循环、≤3 次追问）
   ▼
结构化诊断 JSON（severity / summary / hypotheses[title] / steps / pending_checks）
   + 通俗摘要 → SSE 流式推送 → 落库（含完整工具调用记录）
```

设计要点：

- **检索是模型手里的工具，不是固定流水线**（Agentic RAG）：模型自己决定查不查、查什么、查几轮；单次查询质量由底层检索引擎保证（§5）。
- **工具触发策略写进系统提示词**：只注册工具、不写触发策略，模型会偷懒不查——"涉及故障判断必须先查码表/知识库、用短关键词查、未命中如实说明、禁止凭训练记忆编造结论"均为提示词硬约束。
- **ask_user 受控追问**：缺"只有车主才知道"的场景信息（起病时机、充电习惯、使用环境）时，以消息流内嵌卡片提问（选项点选 + 自由输入 + 前端自动附加「不知道」兜底）；提示词禁止模型自带兜底选项（重复）；未答提问随会话落库，**支持离线续答**（双方不同时在线是常态）；单轮上限 3 次。
- **诊断状态卡自主维护**：主模型每当获得关键事实（车型确认、车主回答、检查结论）即调用 `update_case_notes` 更新会话状态卡（字符串覆盖、列表追加去重）——压缩丢的是对话原文，不丢诊断事实。
- **ask_user 中断恢复**：同一批排在待答 ask_user 之后的工具调用落存根响应行，保证消息序列完整可回放（含异常中断场景，pytest 覆盖）。

### 4.2 工具清单（6 个）

| 工具 | 作用 | 实现层 |
|---|---|---|
| kb_search(查询, 类别, top_k) | 知识库语义检索，可多轮改写查询 | registry + rag |
| dtc_lookup(故障码) | DTC 码表结构化直查（区别于模糊检索） | registry |
| web_search(查询) | Tavily 联网核实，带来源治理（§5.4） | registry + tavily |
| get_vehicle_profile() | 读当前工单车辆档案与历史诊断 | registry |
| ask_user(问题, 字段, 选项) | 向用户提问（卡片、离线续答） | runner |
| update_case_notes(字段) | 模型自主维护诊断状态卡 | runner |

工具数量刻意收敛（6 个）：工具清单膨胀会挤占上下文预算并稀释调用质量，新增工具需评审。

### 4.3 流式协议

`/api/chat` 以 SSE 推送事件流：工具调用开始（含查询词）/ 工具结果（命中数）/ 追问卡片 / 诊断卡 / 完成。车主端只展示轻提示（"正在查询维修资料…"），店员端展示完整证据链——同一引擎、两种呈现。

## 5. 检索引擎（RAG 底座）

### 5.1 导入管道（ingest）

```
解析（MD/TXT/PDF/Word）→ 结构感知分块（保留章节路径 section_path / 页码）
   → 嵌入（bge-m3，1024 维）→ vec_chunks（sqlite-vec vec0 虚表）+ kb_chunks 入库
   → 按文档标题自动去重（可重复执行）
```

内置语料 300+ 条：OBD-II 故障码表 195 条（通用 P0 / P0A 电动车 / U·C 码）+ 电池 / 电机 / 电控 / 充电 / 低温 / 诊断方法 / 指示灯 / 维保养知识 105+ 条，全部标注来源（文档名/章节/页码），不爬付费/版权资料。

### 5.2 检索链路：向量主路 + 重排精排（BM25 仅降级保底）

健康路径为**向量召回 → 云端重排精排**两跳：云端 bge-m3 实测纯向量路显著优于双路 RRF 融合（eval_gate 同批对比：纯向量 top3 命中 100% vs 融合 85%——BM25 在当前语料上是负贡献，会拉低头部精度），召回 top_k 后再经云端 bge-reranker-v2-m3 对「问题-文档」相关性精排，把最相关的块排到最前（实测 top1 命中 82%→86%、同义改写集 75%→83%，top3 不倒退）；重排服务不可达/超时/异常时静默保持原序，检索不中断。向量路不可达（嵌入服务挂 / 扩展缺失）或零召回时，自动退化为 jieba + BM25 关键词路——它只是降级路线，不是健康路径的一环，服务不中断。

- 数量漏斗：候选召回 → 注入 top_k，单条工具结果总预算 4000 字符（参数可调）。
- 每条结果带元数据（文档名 / 章节路径 / 页码 / 得分 / 命中来源 vec|bm25）→ 诊断结论可溯源引用。

**跨环境兼容教训**：sqlite-vec vec0 虚表的 KNN 查询在老 SQLite（如 Ubuntu 22.04 的 3.37）上不接受 `LIMIT :k` 绑定参数进查询计划，必须写成 `k = :k` 专用约束列形式；新版本 SQLite（3.45）两者皆可。代码统一采用约束列写法保证跨环境一致。

### 5.3 红绿闸门评测（eval_gate）

检索质量不是"感觉准"，而是**每次改动可机械判定**：

```
python -m backend.rag.eval_gate

绿线：50 个典型故障问题（eval_set.json，固定种子可复现）top-3 命中率 ≥ 80%
      （当前实测 100%）
红线：注入故障模式必须相对基线下降 ≥ 15%（见红才算测试有效）：
      bm25_only —— 强制只用关键词路（当前 78%，见红）
      vec_noise —— 嵌入向量替换为固定种子噪声（当前 36%，见红）
      shuffle   —— 检索结果乱序（当前 58%，见红）
      （以上为接入重排后的最新实测：绿线基线含云端重排）
```

评测集 50 例由生成脚本从语料锚定生成（校验 doc_key / section / DTC 码真实存在，杜绝虚构条目），覆盖车主口语化描述与专业术语两类查询口径。这一闸门在开发期实际拦下过两次真实回归（RRF 融合负贡献、shuffle 无种子导致的偶发误判）。

### 5.4 联网检索来源治理

web_search 结果不做无脑注入：可信域（车企官网 / 国标 / 专业站）加权上浮，内容农场下沉，零价值域（财经行情 / 搜索结果页 / 文档农场）硬剔除；**仅联网单源支撑的判断降格为「待确认项」，不进诊断结论**——联网证据的置信等级低于知识库与码表。

## 6. 上下文工程与三层记忆

### 6.1 上下文压缩（双阀门）

| 阀门 | 触发 | 动作 |
|---|---|---|
| 1 轮数截断 | 历史超过 20 轮 | 最早轮次不进模型上下文 |
| 2 token 预算 | 估算超 24000 token | 后台压缩模型把更早轮次摘要为前情摘要（≤800 字）注入 |

- 前情摘要与压缩边界持久化（`sessions.context_summary` / `summarized_until_id`）；messages 表原文保留，只是不再进上下文——回看与审计不受影响。
- 压缩模型不可用或失败 → 降级为纯轮数截断（边界同样前移，避免每轮重复失败调用）。
- **压缩为什么不由本地小模型做**：小上下文模型装不下多轮原文，且压缩在主回复链路上同步执行，本地小模型 prefill 延迟不可接受（实测 4B 级模型压缩约 40k token 需 20 秒级）——压缩槽位默认由云端后台模型担任。

### 6.2 注入策略（保护缓存前缀）

云端模型对"开头完全相同的请求"有缓存折扣，因此注入内容的原则是：**要么挂在请求最尾端（不动开头），要么不进历史**。

| 注入物 | 策略 |
|---|---|
| 诊断状态卡 + 车辆档案摘要 + 历史诊断 | 每轮临时拼装在上下文**最尾端**（最新用户消息之前），**不写入对话历史**——下一轮重新拼最新的 |
| 工具结果 | 当轮全文进入历史（下一轮要引用）；单条超长按 4000 字符截断 |
| 首轮兜底预检索结果 | 同状态卡，临时块注入不进历史 |

状态卡刻意不放 system 消息——system 每轮变化会破坏前缀缓存；放尾端则历史前缀保持稳定，日常轮次间持续命中缓存。

### 6.3 三层记忆

1. **会话内 · 诊断状态卡**：结构化字段（车型/VIN/症状/已排查项/待确认项），主模型经 `update_case_notes` 自主维护；新会话开场由本地小模型从首条描述**异步**抽取初稿（不阻塞主流程，失败留空）。
2. **跨会话 · 车辆档案**：按 VIN/车牌归档，新会话自动加载该车历史诊断；车主默认车自动带入。
3. **门店 · 案例库**：技师确认维修结果后一键沉淀为案例，自动记录入库并纳入后续诊断的检索范围（数据飞轮）。

## 7. 数据模型

SQLite 单文件，12 张业务表（全部带 `tenant_id`，多店隔离从第一天预留）：

| 表 | 职责 |
|---|---|
| users | 账号：用户名、PBKDF2 密码指纹、角色（owner/staff/admin/superadmin）、租户 |
| vehicle_profiles | 车辆档案（VIN/车牌/车型/历史诊断汇总） |
| owner_vehicles | 车主 ↔ 车辆绑定（含默认车标记） |
| sessions / messages | 会话与消息（含工具调用记录、状态卡 case_notes、前情摘要、token 用量） |
| kb_documents / kb_chunks | 知识库文档与结构化分块（章节路径/页码，引用溯源的锚点） |
| cases | 门店沉淀案例（技师确认的诊断结论，回流检索范围） |
| appointments | 预约单：车辆、诊断摘要卡、时间/门店、状态机流转、维修结果回填 |
| provider_configs | 模型供应商槽位配置（**不含密钥**——密钥只住 config.json） |
| usage_stats | 每次模型调用的 token / 供应商 / 成本流水（管理端看板，未来计费基础） |
| audit_logs | 审计日志：谁在什么时间做了什么关键操作 |

另有两张引擎管理的附属结构：`vec_chunks`（sqlite-vec vec0 虚表，存嵌入向量）与 BM25 内存索引（jieba 分词，基于 kb_chunks 构建缓存）。

## 9. 安全设计

| 维度 | 实现 |
|---|---|
| 密钥 | 全部后端配置管理；前端构建产物零密钥（发布前模式扫描核验） |
| 密码 | PBKDF2-SHA256（240k 迭代）；改密码强制强度校验（≥8 位、字母+数字、不得含账号名），且不允许改回"密码=账号名"弱口令 |
| 会话 | JWT（7 天）；四角色接口级鉴权 |
| 登录限速 | 按账号计数，15 分钟窗口 5 次失败即锁（锁定期不做密码校验直接拒绝），成功清零，锁定写审计（`login_locked`）；单进程内存实现 |
| 越权 | 跨账号会话/工单一律 404 不泄露存在性；车主隐私开关由后端 403 强制（非前端隐藏） |
| 隐私 | 预约单诊断摘要卡始终对店员可见；对话原文仅在车主开启分享开关后随工单可见 |
| superadmin | 首启自动建号，20 位随机密码每次启动打印到后端终端；明文仅存 config.json（与 API Key 同一密钥宿主）；不进仓库/数据库/接口响应；接口组独立且对 admin 完全隔离 |
| 审计 | 登录成功/失败/锁定、建号、停用、重置密码、预约流转、隐私变更、密码修改 → audit_logs |

## 10. 部署架构

### 10.1 拓扑（当前生产形态）

```
用户浏览器
   │  HTTPS
   ▼
Cloudflare 边缘（TLS 终止 · DNS）
   │  隧道（cloudflared --protocol http2，纯出站连接）
   ▼
云服务器（Ubuntu 22.04）
   ├── systemd: nev-diag.service      → .venv/bin/python main.py --host 127.0.0.1 --port 8600
   ├── systemd: cloudflared.service   → 隧道 ingress: 域名 → http://127.0.0.1:8600
   └── /opt/nev-diag/                 → 项目目录（data/ 含密钥与数据库）
```

- **同源直达**：前端静态托管与 API 同进程同域名，"访问域名即进入系统"，CORS / 混合内容 / 前端接入地址配置一律不需要。
- **为什么走隧道而不是安全组放行**：安全组零入站规则（cloudflared 纯出站）；TLS 在边缘终止，服务器不装证书；源站 IP 不进 DNS（扫描与直连攻击面收窄）；攻击流量消耗 Cloudflare 边缘而非服务器带宽。实测该云环境 QUIC（UDP 7844）链路劣化，隧道固定 `--protocol http2` 后稳定。
- **演进路径**：域名完成 ICP 备案后，可切回 443 标准端口直连（Caddy/Nginx TLS → 8600），隧道退役或保留为备用通道。
- **迁移 = 拷目录**：`/opt/nev-diag` 整目录（含 data/）拷至新机 + 两个 systemd unit 即完成迁移，无外部中间件。

### 10.2 部署要点

- Python 虚拟环境 + 国内 PyPI 镜像；前端在构建机 `npm run build` 后随目录分发（服务器无需 Node）。
- 首启自动建表、建演示账号与演示车辆；`python -m backend.seed.load_corpus` 导入内置知识库（幂等）。
- 生产前删库重建（README「生产重置」）；superadmin 密码从启动终端领取，遗忘时 `python main.py --reset-superadmin` 重新生成。

## 12. 关键设计决策记录

部分机制设计参考了 AstrBot 等开源 AI 应用的公开实践与实测结论；以下决策均以本系统实测数据为最终依据。

| # | 决策 | 依据 |
|---|---|---|
| D1 | 单体应用、无 Docker、SQLite 单文件 | 单店场景无并发压力；拷目录即迁移；ORM 隔离为将来升级留门 |
| D2 | 检索 = 向量主路 + BM25 降级保底（弃 RRF 融合） | eval_gate 实测：纯向量 top3 100% vs 双路融合 85%，BM25 在本语料是负贡献；保留为嵌入不可用时的降级路径 |
| D3 | 评测集 50 例 + 固定种子 + 故障注入见红 | 首版 20 例无种子导致 shuffle 模式偶发误判（flaky）；扩集锚定生成杜绝虚构条目 |
| D4 | 重排：bge-reranker-base 默认关 → 换型 v2-m3 后启用 | 初代 bge-reranker-base 困难模式 top-1 命中 64%、0.1 分阈值把正例整组滤掉（净损失召回），故预留钩子默认关；2026-10-02 换型 bge-reranker-v2-m3 重跑同一评测集实测通过（top1 82%→86%、改写集 75%→83%、top3 不倒退），定参候选池=top_k 纯重排（分数阈值可分性弱，默认 0），转默认启用 |
| D5 | 压缩由云端后台模型担任，本地小模型不碰 | 4B 级模型压缩 ~40k token prefill 20 秒级且上下文装不下多轮原文；压缩在主回复链路上同步执行 |
| D6 | 本地小模型只做异步单步任务（抽取/标题） | 失败静默降级不影响主流程；决策权始终在主模型 |
| D7 | 状态卡尾端临时注入、不进历史 | 保护模型前缀缓存（重复开头按折扣计费且更快）；system 消息每轮变化会击穿缓存 |
| D8 | ask_user 卡片化 + 离线续答 + 单轮上限 3 | 提问是能力，滥用要防；车主与系统不同时在线是常态，待答提问必须可持久化续答 |
| D9 | 联网检索来源治理 + 单源降格 | 内容农场污染与过度自信是联网 RAG 两大失效模式；联网证据置信低于知识库/码表 |
| D10 | 同源部署 + Cloudflare 隧道（http2） | 零入站安全组、TLS 边缘终止、源站 IP 不进 DNS；QUIC 在该云环境实测劣化固定 http2；备案后可切 443 直连 |
| D11 | sqlite-vec 用 `k = :k` 约束列写法 | 老 SQLite（3.37）不接受 `LIMIT :k` 绑定参数进 vec0 查询计划，新版本两者皆可——约束列写法跨环境一致 |
| D12 | superadmin 独立角色 + 接口组隔离 | 面向公网的运维通道不能与业务管理员混权；密码仅启动终端打印，不进任何持久面 |

## 13. 已知限制与演进方向

| 限制 | 现状 | 演进 |
|---|---|---|
| 公网经非标端口 8600 | 试用实例不满足 ICP 备案条件 | 备案通过后切 443 直连 |
| 检索索引未按租户分片 | 所有租户共享内置知识库 | 多租户商用前按 tenant_id 分片或加元数据过滤 |
| 登录限速为单进程内存态 | 多实例部署会失效 | 换集中存储（Redis 等） |
| 单进程纵向扩展上限 | FastAPI 单 worker 已满足单店负载 | 多实例化需同时处理：限速集中存储、SQLite → PG、会话亲和 |
| 重排增益有限 | 当前语料上 top3 已 100% 饱和、top1 +4pp | 更大语料下用同一评测集方法重评收益；配置可一键关闭 |
| 语料与评测集规模 | 内置 300+ 条 / 评测 50 例 | 随案例回流持续扩充，评测集同步扩容 |
